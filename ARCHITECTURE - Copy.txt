## Executive Summary

This test automation framework is a sophisticated, enterprise-grade solution built on Playwright, implementing modern software engineering principles including SOLID, DRY, and Domain-Driven Design. The architecture emphasizes maintainability, scalability, and code reusability through a multi-tier layered approach with clear separation of concerns.

### Key Highlights

- **Multi-Domain Architecture**: Organized by business domains (basesAI, dreamQ, forecasting, reporting, studio, projectService)
- **Design Patterns**: Page Object Model (POM), Dependency Injection, Facade, Composition over Inheritance
- **Security First**: Path traversal protection, sensitive data masking, secure logging
- **Parallel Execution**: Fully parallel test execution with 4 workers
- **Hybrid Testing**: Combined UI and API testing capabilities
- **CI/CD Ready**: Azure DevOps pipeline integration with comprehensive reporting

## Architectural Layers

### 1. Test Layer (`tests/`)

**Purpose**: Contains the actual test cases that validate application functionality.

**Organization**: Domain-driven folders
- `tests/basesAI/` - Tests for Bases AI domain
- `tests/dreamQ/` - Tests for Dream Q domain
- `tests/forecasting/` - Tests for forecasting features
- `tests/projectService/` - Tests for project service
- `tests/reportingService/` - Tests for reporting features
- `tests/studio/` - Tests for studio features

**Key Characteristics**:
- Uses Playwright's extended `test()` function with custom fixtures
- Focuses on business logic and test scenarios
- Leverages dependency injection for page objects and API helpers
- Isolated and independent test execution

**Example Test Structure**:
```typescript
test('Verify workspace creation', async ({ homePage, workspacePage, homePageApi }) => {
    // Test uses injected page objects
    await homePage.gotoHomePage();
    await homePage.createWorkspace();
    await workspacePage.verifyWorkspaceCreated();
});
```

---

### 2. Page Object Layer (`pages/`)

**Purpose**: Implements the Page Object Model (POM) pattern to encapsulate page elements and interactions.

**Organization**: Mirrored domain structure from tests
- `pages/basesAI/` - Page objects for Bases AI
- `pages/dreamQ/` - Page objects for Dream Q
- `pages/forecasting/` - Page objects for forecasting (uses BasePage inheritance)
- `pages/reportingPage/` - Page objects for reporting (uses composition pattern)
- `pages/projectService/` - Page objects for project service
- `pages/studio/` - Page objects for studio

**Two Abstraction Approaches**:

#### Approach 1: Inheritance-Based (Forecasting Domain)
```typescript
// BasePage.ts - Base class with common functionality
export class BasePage {
    readonly page: Page;
    constructor(page: Page) {
        this.page = page;
    }
    // Common methods and properties
}

// Child pages extend BasePage
export class ForecastHomePage extends BasePage {
    // Specific functionality
}
```

#### Approach 2: Composition-Based (Reporting Domain)
```typescript
// ReportingCommonPage.ts - Reusable common page
export class ReportingCommonPage {
    constructor(public readonly page: Page) { }
    // Common reporting methods (597 lines)
}

// Other pages compose ReportingCommonPage
export class InsightsPage {
    constructor(public readonly page: Page) { }
    public readonly reportingCommonPage = new ReportingCommonPage(this.page);
}
```

**Encapsulation**:
- Locators defined as class properties
- Page-specific actions as methods
- Returns data or performs assertions
- Hides implementation details from tests

### 3. Fixture Layer (`fixtures/`)

**Purpose**: Implements Dependency Injection pattern using Playwright's fixture system.

**Organization**: Domain-specific fixture files
- `fixtures/basesAI/HomePage.ts`
- `fixtures/dreamq/SurveyTemplatePage.ts`
- `fixtures/Forecasting/ForecastingPage.ts`
- `fixtures/reporting/ReportingPage.ts`
- `fixtures/projectService/homePage/`

**Key Features**:
- Extends Playwright's base test
- Creates and manages page object instances
- Provides automatic dependency injection
- Handles setup and teardown

**Example Fixture Implementation**:
```typescript
import { test as baseTest } from '@playwright/test';
import { HomePage } from '@pages/basesAI/HomePage';
import { HomePageApi } from 'api/basesAI/HomePageApi';

type pages = {
    homePage: HomePage;
    homePageApi: HomePageApi;
};

export const test = baseTest.extend<pages>({
    homePage: async ({ page }, use) => {
        await use(new HomePage(page));
    },
    homePageApi: async ({ page }, use) => {
        await use(new HomePageApi(page));
    },
});
```

## Design Patterns

### 1. Page Object Model (POM)

**Definition**: Design pattern that creates an object repository for web UI elements, separating page structure from test logic.

**Implementation**:
```typescript
export class HomePage {
    constructor(public readonly page: Page) { }
    
    // Locators
    private addWorkspaceButton = 'SR_homepage_button_addworkspace';
    
    // Actions
    public async gotoHomePage() {
        await this.page.goto(ENV.homePageUrl);
        await this.page.waitForLoadState('networkidle');
    }
    
    public async createWorkspace() {
        await this.page.getByTestId(this.addWorkspaceButton).click();
    }
}
```

**Benefits**:
- Reduces code duplication
- Improves test maintainability
- Makes tests more readable
- Easy to update when UI changes

---

### 2. Dependency Injection (DI)

**Definition**: Pattern where dependencies are provided to a class rather than created by the class itself.

**Implementation**: Playwright Fixtures

**Example**:
```typescript
// Fixture defines dependencies
export const test = baseTest.extend<pages>({
    homePage: async ({ page }, use) => {
        await use(new HomePage(page));
    },
});

// Test receives dependencies automatically
test('example', async ({ homePage }) => {
    // homePage is automatically injected
    await homePage.gotoHomePage();
});
```

**Benefits**:
- Loose coupling between test and page objects
- Easier to mock/stub for unit testing
- Automatic lifecycle management
- Cleaner test code

---

### 3. Facade Pattern

**Definition**: Provides a simplified interface to a complex subsystem.

**Implementation**:

#### ReportingCommonPage (597 lines)
```typescript
export class ReportingCommonPage {
    // Simplified methods hiding complex operations
    public async goToDeliverablePage(reportId: string, endPoint: string) {
        const deliverableURL = this.reportingUrl + reportId + endPoint;
        await this.page.goto(deliverableURL);
    }
    
    public async createInsight(insightText?: string): Promise<string> {
        // Complex logic hidden behind simple interface
    }
}
```

#### BasePage (Forecasting)
```typescript
export class BasePage {
    // Common operations exposed through simple methods
    async homePageLoad() { /* ... */ }
    async setDropdownText(text: string, visible = false) { /* ... */ }
}
```

**Benefits**:
- Simplifies complex operations
- Reduces learning curve
- Promotes code reuse
- Easier to refactor underlying implementation

---

### 4. Composition Over Inheritance

**Definition**: Favor object composition over class inheritance for code reuse.

**Implementation in Reporting Domain**:
```typescript
export class InsightsPage {
    // Composition: "has-a" relationship
    public readonly reportingCommonPage = new ReportingCommonPage(this.page);
    
    public async goToInsightsPage(reportId: string) {
        // Delegates to composed object
        await this.page.goto(
            this.reportingCommonPage.reportingUrl + reportId + '/insights'
        );
    }
}

export class ReportingCommonPage {
    // Multiple composed utilities
    public readonly exportUtils = new ExportUtils(this.page);
    public readonly reportingSetUp = new ReportingSetUpPage(this.page);
}
```

**Comparison**:
- **Forecasting Domain**: Uses inheritance (`extends BasePage`)
- **Reporting Domain**: Uses composition (instantiates common classes)

**Benefits of Composition**:
- More flexible than inheritance
- Avoids deep inheritance hierarchies
- Runtime behavior modification
- Better encapsulation

---

### 5. Factory Pattern (Implicit)

**Definition**: Creates objects without specifying exact class.

**Implementation**: Through Fixtures
```typescript
// Fixture acts as factory
export const test = baseTest.extend<pages>({
    homePage: async ({ page }, use) => {
        await use(new HomePage(page)); // Factory creates HomePage
    },
});
```

**Benefits**:
- Centralized object creation
- Easy to change implementation
- Consistent object initialization

---

### 6. Strategy Pattern

**Definition**: Defines a family of algorithms, encapsulates each one, and makes them interchangeable.

**Implementation**:
- Different authentication strategies per environment
- Multiple browser configurations (Chromium, Chrome)
- Environment-specific configurations

**Example**:
```typescript
// playwright.config.ts
projects: [
    {
        name: 'chromium',
        use: { ...devices['Desktop Chrome'] },
    },
    {
        name: 'Google Chrome',
        use: { ...devices['Desktop Chrome'], channel: 'chrome' },
    },
]
```

## SOLID Principles Implementation

### 1. Single Responsibility Principle (SRP)

**Definition**: A class should have only one reason to change.

**Implementation**:
- **HomePage**: Only handles home page operations
- **WorkspacePage**: Only handles workspace operations
- **ReportingSetUpPage**: Only handles report setup
- **ExportUtils**: Only handles export operations

**Example**:
```typescript
// Each class has single, well-defined responsibility
export class HomePage {
    // Only home page related methods
    public async gotoHomePage() { /* ... */ }
    public async createWorkspace() { /* ... */ }
}

export class ExportUtils {
    // Only export related methods
    public async exportToPNG() { /* ... */ }
    public async exportToExcel() { /* ... */ }
}
```

---

### 2. Open/Closed Principle (OCP)

**Definition**: Software entities should be open for extension but closed for modification.

**Implementation**:
- **BasePage** can be extended by new page classes without modification
- **Fixtures** can be extended with new page objects
- **Composition** allows adding new capabilities without changing existing code

**Example**:
```typescript
// BasePage is closed for modification, open for extension
export class BasePage {
    // Core functionality remains unchanged
}

// New pages extend without modifying BasePage
export class NewFeaturePage extends BasePage {
    // Adds new functionality
}
```

---

### 3. Liskov Substitution Principle (LSP)

**Definition**: Objects of a superclass should be replaceable with objects of its subclasses.

**Implementation**:
- Any page extending `BasePage` can be used where `BasePage` is expected
- All pages implement consistent interface patterns

**Example**:
```typescript
// All forecasting pages can substitute BasePage
function operateOnPage(page: BasePage) {
    // Works with BasePage or any child class
    page.homePageLoad();
}

// Can pass any child page
operateOnPage(new ForecastHomePage(page));
operateOnPage(new ConceptSKUPage(page));
```

---

### 4. Interface Segregation Principle (ISP)

**Definition**: Clients should not be forced to depend on interfaces they don't use.

**Implementation**:
- Specific interfaces for different data types
- Page classes only expose relevant methods
- No monolithic interfaces

**Example**:
```typescript
// Specific interface for Excel data
export interface ExcelDataItem {
    locale: string;
    segmentId: string;
    subgroup: number;
    // ... only Excel-related fields
}

// Specific interface for User data
export interface UserDetails {
    user: string;
    email: string;
    password: string;
    // ... only user-related fields
}
```

---

### 5. Dependency Inversion Principle (DIP)

**Definition**: High-level modules should not depend on low-level modules. Both should depend on abstractions.

**Implementation**:
- Tests depend on Page interface abstraction (Playwright's `Page`)
- Page objects depend on `Page` abstraction, not concrete browser implementation
- Dependency Injection through fixtures

**Example**:
```typescript
// Depends on Page abstraction, not concrete implementation
export class HomePage {
    constructor(public readonly page: Page) { }
    // Page is an abstraction, not concrete browser
}

// Test depends on abstraction
test('example', async ({ page }) => {
    const homePage = new HomePage(page); // page is abstraction
});
```

## OOPs Concepts Applied

### 1. Encapsulation ✅

**Definition**: Bundling data and methods that operate on that data within a single unit, with controlled access.

**Implementation**:

#### Public vs Private Members
```typescript
export class ReportingSetUpPage {
    // Public - accessible externally
    public cerberusAPI = new GetCerberusTokenAPI(this.page);
    public responseToken: string = '';
    public returnedReportId: string = '';
    
    // Private - hidden implementation
    private minNumber: number = 11111;
    private maxNumber: number = 99999;
    private conceptImageHeight = 450;
    private reportName: string = `...`;
}
```

**Benefits**:
- Hides internal implementation
- Provides controlled access
- Prevents unauthorized data modification
- Easier to maintain and refactor

---

### 2. Abstraction ✅

**Definition**: Hiding complex implementation details and showing only essential features.

**Implementation**:

#### Interface Abstraction
```typescript
export interface ExcelDataItem {
    locale: string;
    segmentId: string;
    subgroup: number;
    exerciseConceptId: number;
    concept: string;
    // ... hides internal structure complexity
}
```

#### Method Abstraction
```typescript
// Complex URL construction hidden
public async goToDeliverablePage(reportId: string, endPoint: string) {
    const deliverableURL = this.reportingUrl + reportId + endPoint;
    await this.page.goto(deliverableURL);
    // User doesn't need to know URL construction details
}
```

**Benefits**:
- Reduces complexity
- Focuses on "what" not "how"
- Easier to use and understand
- Flexible implementation changes

---

### 3. Inheritance ✅

**Definition**: Mechanism where a new class inherits properties and methods from an existing class.

**Implementation in Forecasting Domain**:

#### Single Inheritance
```typescript
export class BasePage {
    readonly page: Page;
    // Common properties and methods
    async homePageLoad() { /* ... */ }
}

export class ForecastHomePage extends BasePage {
    // Inherits all BasePage functionality
    // Adds specific functionality
}
```

#### Multi-Level Inheritance
```typescript
export class AdvertisingPage extends BasePage {
    // Level 2
}

export class EasyPlanAdvertisingPage extends AdvertisingPage {
    // Level 3 - inherits from AdvertisingPage and BasePage
}
```

**Benefits**:
- Code reuse
- Hierarchical classification
- Polymorphic behavior
- Extensibility

---

### 4. Polymorphism ✅

**Definition**: Ability of different classes to be treated as instances of the same class through inheritance or interfaces.

**Implementation**:

#### Method Overloading (Parameter Polymorphism)
```typescript
// Optional parameters allow different calling patterns
public async setUpReporting(
    conceptNames?: string[], 
    conceptIDs?: number[], 
    subgroupNames?: string[],
    // ... many optional parameters
): Promise<string[]> {
    // Behaves differently based on provided parameters
}

// Can be called in multiple ways:
await setUpReporting();
await setUpReporting(conceptNames, conceptIDs);
await setUpReporting(conceptNames, conceptIDs, subgroupNames, subgroupIDs);
```

#### Function as Property (Higher-Order Function)
```typescript
public readonly barChartValueLocator = (row: number, column: number) => 
    this.page.locator(`tbody tr:nth-child(${row}) td:nth-child(${column})`);

// Polymorphic behavior based on parameters
const locator1 = barChartValueLocator(1, 2);
const locator2 = barChartValueLocator(5, 3);
```

**Benefits**:
- Flexible code
- Runtime behavior selection
- Reduces conditional logic
- Cleaner interfaces

## Domain-Driven Design

### Domain Organization

The framework follows **Domain-Driven Design (DDD)** principles with clear domain boundaries:

```
Domains:
├── basesAI          - AI-powered market research platform
├── dreamQ           - Survey and questionnaire management
├── forecasting      - Sales forecasting and planning
├── projectService   - Project and collaboration management
├── reportingService - Analytics and reporting
└── studio           - Content creation and analytics studio
```

### Benefits of Domain-Driven Structure

1. **Clear Boundaries**: Each domain is self-contained with its own pages, tests, fixtures, and APIs
2. **Team Scalability**: Multiple teams can work on different domains without conflicts
3. **Easier Navigation**: Intuitive folder structure based on business domains
4. **Isolated Changes**: Changes in one domain don't affect others
5. **Domain Expertise**: Tests and code organized by business capabilities

### Cross-Domain Communication

```typescript
// Domains can share utilities but maintain independence
import CommonUtil from '@utils/commonUtils/CommonUtil';
import { ExportUtils } from '@utils/dataUtils/exportUtils/ExportUtils';

// Each domain has its own API namespace
import { HomePageApi } from 'api/basesAI/HomePageApi';
import { CreateReportAPI } from 'api/reporting/CreateReportAPI';
```

## Configuration Management

### Playwright Configuration (`playwright.config.ts`)

```typescript
{
    // Global setup runs before all tests
    globalSetup: './utils/globalSetup',
    
    // Test directory
    testDir: './tests',
    
    // Default options for all tests
    use: {
        baseURL: process.env.baseURL,        // From environment
        headless: false,                     // Browser visibility
        trace: 'retain-on-failure',          // Trace recording
        screenshot: 'only-on-failure',       // Screenshot capture
        navigationTimeout: 30_000,           // 30 seconds
        actionTimeout: 8_000,                // 8 seconds
    },
    
    // Browser configurations
    projects: [
        {
            name: 'chromium',
            use: { ...devices['Desktop Chrome'], acceptDownloads: true },
        },
        {
            name: 'Google Chrome',
            use: { ...devices['Desktop Chrome'], channel: 'chrome' },
        },
    ],
    
    // Test execution settings
    timeout: 120_000,              // 2 minutes per test
    fullyParallel: true,           // Run all tests in parallel
```

## Security Architecture

### 1. Path Traversal Protection

**Location**: `utils/PathUtils.ts`

**Purpose**: Prevent malicious path access outside repository boundaries

**Implementation**:
```typescript
export function sanitizePath(inputPath: string): string {
    // Remove path separators, parent directory references
    const sanitized = inputPath.replace(/[/\\]/g, '_')
                               .replace(/\.\./g, '_');
    // Validate alphanumeric, dash, underscore, dot only
    if (!/^[a-zA-Z0-9_\-\.]+$/.test(sanitized)) {
        throw new Error('Invalid characters in path');
    }
    return sanitized;
}

export function safeJoin(base: string, ...parts: string[]): string {
    const resolved = path.resolve(base, ...parts);
    // Ensure result is within base directory
    if (!resolved.startsWith(base)) {
        throw new Error('Path traversal detected');
    }
    return resolved;
}
```

**Usage**:
```typescript
// Safe file operations
const sanitizedPath = sanitizePath('test-data/users.csv');
const fullPath = safeJoin(process.cwd(), sanitizedPath);
```

---

### 2. Sensitive Data Masking

**Location**: `utils/globalErrorHandler.ts`

**Purpose**: Prevent sensitive information from appearing in logs

**Implementation**:
```typescript
export function logMessage(message: string, ...args: any[]) {
    const maskedMessage = maskSensitiveData(message);
    const maskedArgs = args.map(arg => 
        typeof arg === 'string' ? maskSensitiveData(arg) : arg
    );
    console.log(maskedMessage, ...maskedArgs);
}

function maskSensitiveData(text: string): string {
    // Mask passwords, tokens, credentials
    return text
        .replace(/password["\s:=]+([^"\s,}]+)/gi, 'password=***')
        .replace(/token["\s:=]+([^"\s,}]+)/gi, 'token=***')
        .replace(/api[_-]?key["\s:=]+([^"\s,}]+)/gi, 'apikey=***');
}
```

**Enforcement**:
- ❌ **Forbidden**: `console.log()`, `console.warn()`, `console.error()`
- ✅ **Required**: `logMessage()`, `handleError()` from globalErrorHandler

## Testing Strategy

### Test Isolation

**Principle**: Each test should be independent and able to run in any order

**Implementation**:
1. **Fresh Browser Context**: Each test gets isolated browser context
2. **Clean State**: Setup/teardown in fixtures
3. **No Test Dependencies**: Tests don't rely on other tests
4. **Parallel Execution Safe**: No shared mutable state

```typescript
test.beforeEach(async ({ page }) => {
    // Fresh state for each test
    await setupTestData();
});

test.afterEach(async ({ page }) => {
    // Cleanup after each test
    await cleanupTestData();
});
```

---

### Hybrid Testing Approach

**UI + API Testing**: Combine strengths of both approaches

#### Typical Flow:
```
1. API Setup (FAST)
   └─→ Create test data via API
   └─→ Setup preconditions

2. UI Testing (VISUAL VERIFICATION)
   └─→ Navigate to page
   └─→ Verify visual elements
   └─→ Test user interactions

3. API Assertions (FAST & RELIABLE)
   └─→ Verify backend state
   └─→ Check data consistency

4. API Cleanup (FAST)
   └─→ Delete test data
   └─→ Reset state
```

#### Benefits:
- **Speed**: API calls faster than UI navigation
- **Reliability**: Less flaky than pure UI tests
- **Coverage**: Tests both UI and API layers
- **Maintainability**: Setup/cleanup via stable API
